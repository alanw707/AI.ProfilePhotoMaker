# ADR 0009: Career agent runs are durable, leased, fenced step machines

Status: accepted (2026-10-04, ticket #380, spec #376)

## Context

#380 proves the career-agent runtime with one narrow task: draft a profile summary and save it as a reviewable proposal. The task must survive restarts and crashes, run on more than one worker, be cancellable, never spend twice, and never change profile facts by itself. The provider was a human gate on #380; the owner chose OpenAI on 2026-10-05 (see below). The specific model and its prices stay configuration.

## Decision

- **Model seam, fail closed.** `ICareerTextModel` takes a structured request (task, pinned facts, allowed tool names) and returns either a final text or a tool call, plus usage and cost. `FakeCareerTextModel` (deterministic, no network) is the default for Development, LocalDev and Testing. **Production registers no model unless one is configured, so `POST /api/career/runs` answers 503 `CareerModelUnavailable`.**
- **Provider: OpenAI (decided 2026-10-05, #380).** `OpenAICareerTextModel` calls the Responses API and is registered in any environment once `OpenAI:ApiKey` (shared with the photo features), `Career:Agent:Model`, `Career:Agent:InputUsdPerMillionTokens` and `Career:Agent:OutputUsdPerMillionTokens` are all set; without prices the cost ceiling could not be enforced, so it stays off, and a partly configured model logs which settings are missing (names only) at startup. No model name or price is written in code. Requests use a strict JSON schema (`{ "summary": string }`), `store: false`, `max_output_tokens` (default 400), `reasoning.effort` only when `Career:Agent:ReasoningEffort` is set (needed to keep reasoning models inside the output limit), and no tool definitions (the pinned facts already answer `read_profile`/`read_goal`). Profile and goal values go only in the user input as JSON; the instructions tell the model that this JSON is data, not instructions. Cost is computed from returned token usage and configured prices, rounded up to whole cents. A paid response that cannot be used (malformed, refused, incomplete) still carries its cost, and the runner adds it to the run before the cost ceiling check; a response without usage is charged conservatively (request size as input plus the whole output allowance).
  - **Timeout.** Each call is cancelled after `LeaseSeconds − 5` (25 s by default), inside the lease, by both the adapter and the runner.
  - **Errors.** Retryable (the runner backs off and retries up to `MaxAttempts`): network failures, timeouts, 408/409/429, 5xx, `incomplete`/`failed` responses and output that does not match the schema. Fatal (the run fails `CareerModelFailed` at once): 400/401/403/404/422, a 429 `insufficient_quota`, a refusal, a response cut off by `max_output_tokens` (the same limit applies on every retry) and an unsupported task. Unknown response statuses are logged as `unknown`, never echoed. A started call always spends the run's one allowance unit.
  - **Logs** carry HTTP status, error code, the provider `x-request-id` and the run id; never prompts, outputs or provider messages, which can echo the prompt.
  - **Retention and privacy terms** (OpenAI API data controls as published at decision time; re-check before launch): API inputs and outputs are not used for training by default; `store: false` keeps the response out of OpenAI's stored-response history; OpenAI may still keep abuse-monitoring logs for up to 30 days unless the organisation is approved for Zero Data Retention. Before production rollout the owner confirms the organisation's data-control settings, decides whether to request ZDR, and adds OpenAI as a subprocessor in the privacy notice. Profile text sent is limited to confirmed career facts; resumes are never sent by this task.
  - **Live check.** `OpenAICareerTextModelLiveTests` makes one real call and is skipped unless `OPENAI_API_KEY` and `CAREER_AGENT_MODEL` are set.
- **Persistence.** `CareerAgentRun` (one per request) and `CareerAgentStep` (one per executed step). Run status: `queued → working → (needs_input ↔ working) → completed | failed | cancelled`. A run pins the profile version and goal version it read at creation. Steps have a stable operation id `"{runId}:{ordinal}"` (unique), a kind (`tool`, `model`, `question`, `save`), and their output. The run stores a checkpoint (next ordinal + small JSON state).
- **Lease and fencing.** A worker claims a run by setting `LeaseOwner`, `LeaseExpiresAt` and incrementing `FencingToken`, which is an EF concurrency token. Every later write by that worker carries the token it claimed with; if another worker re-claimed after lease expiry, or the user cancelled, the stale write fails as a concurrency conflict and is discarded. Expired leases (`working` with `LeaseExpiresAt` in the past) are claimable again. **Every terminal write (completion, failure, ceiling, retry limit, question expiry, cancel) also bumps the token**, so a worker whose lease expired mid-call can never write over a run another writer has already ended. The fence check compares the stored token with the one the worker loaded, not with a value the same save is about to bump.
- **Model call accounting and bounds.** `ModelCalled` is saved (fenced, renewing the lease) *before* the provider is asked, so a crash, cancel or lost lease during the call still counts the started call. The call is cancelled after `LeaseSeconds − 5` seconds (at least 1), well inside the lease, so no second worker can claim the run and ask the provider again while the first call is in flight. A failed or timed-out call is retried only after `RetryBackoffSeconds × attempts` (default 5 s), held back by using `LeaseExpiresAt` as "not before" on the queued run. The cost ceiling is checked when a call returns, so one call can exceed `MaxCostCents`; the run then fails without using the result.
- **Crash after provider response.** The model step's output is saved (with the step) before anything uses it. On resume, a step that already has saved output is replayed from storage, never called again, so a crash between the provider answer and the proposal save costs exactly one provider call.
- **Idempotency.** `POST /api/career/runs` requires an `Idempotency-Key` header (8–100 chars). Key + owner is unique; the server stores a SHA-256 of the normalized request body. Same key and same body → the existing run (202, same id, no second reservation). Same key, different body → 409 `CareerIdempotencyMismatch`. A lost race on the unique index reloads the winner.
- **Tool allowlist and owner scope.** The task definition lists the tools it may use (`read_profile`, `read_goal`). Tools resolve data only for the run's owner and pinned versions. A model asking for any other tool fails the run with `CareerToolNotAllowed` and no side effect. Document and profile text are data, never instructions.
- **Proposal, never a fact.** The final `save` step creates a `CareerProfileProposal` with `Source = "agent"` and one `summary` item, pinned to the run's profile version, in the same save that completes the run. Accepting it uses the existing proposal flow; if the profile changed since the run pinned it, acceptance answers 412 and the run status reports `profileChanged: true`.
- **Questions.** If the owner has no goal, the task asks one question ("Who should this summary speak to?") and waits in `needs_input`; `POST /runs/{id}/answers` resumes it. A needs-input run does not hold a lease. A question unanswered for `QuestionExpiryHours` (default 72) fails the run with `CareerQuestionExpired` and releases its allowance unit, so abandoned questions cannot use up the month.
- **Cancel.** `POST /runs/{id}/cancel` is idempotent. It sets `cancelled` and bumps the fencing token, so a worker that finishes late cannot complete the run or create a proposal. Cancelling a finished run returns its final state unchanged.
- **Ceilings (config `Career:Agent`).** `MaxSteps` 8, `MaxRunSeconds` 120, `MaxAttempts` 3 (claims per run; retries after transient failures or lease expiry), `LeaseSeconds` 30, `MaxCostCents` 5, `MonthlyRunAllowance` 20. Exceeding any ceiling fails the run with a stable code (`CareerStepLimit`, `CareerTimeLimit`, `CareerRetryLimit`, `CareerCostLimit`).
- **Career allowance, separate from photo credits.** `CareerAllowance` (owner + UTC month, `Reserved`, `Used`, concurrency token). Creating a run reserves one unit; it is settled (reserved → used) when the run ends after a model call was started (even one that failed, timed out or was cancelled mid-flight, since the provider may have billed it), and released if the run ends before any model call (cancel, failure, ceiling, expired question). A run uses at most one unit however many retries it needs. No reservation when the month is full: 429 `CareerAllowanceExhausted`. Reads (status, list, proposals) are free; old runs and proposals stay readable.
- **Worker.** `CareerAgentWorker` (hosted service, `Career:Agent:WorkerEnabled`, off in Testing) polls for claimable runs; tests drive `ICareerAgentRunner.RunOnceAsync(workerId)` directly with a controllable clock.
- **Privacy and retention.** Runs, steps and allowances carry `OwnerId`, cascade on account deletion and join `CareerPrivateDataService` deletion coverage. Logs carry ids and codes only. Retention follows profile versions and proposals (ADR 0006/0007): runs and their steps (which hold the drafted text) are kept while the account exists, so old results stay readable, and are removed with the account or by the career deletion control. Allowance rows hold only monthly counters and follow the same rule. User-facing export and per-item deletion arrive with #392, which must include these entities.
- **Structured tool use.** The request names the allowed tools; in this task the pinned facts already answer them, so the runner executes `read_profile`/`read_goal` as fixed steps and treats any model tool request as a failure (`CareerToolNotAllowed` for an unlisted tool). Model-driven tool execution arrives with the market tools.

## Consequences

- SQL Server-specific guarantees (unique index violations 2601/2627, row-version races under real isolation) are simulated in tests on the in-memory provider; proving them against a real SQL Server remains a gate until a SQL Server test host exists.
- Progress shown to users is the list of real completed steps and the current status; there is no percentage and no model reasoning transcript.
