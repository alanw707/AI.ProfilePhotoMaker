# ADR 0016: Roadmaps are deterministic, evidence-gated proposals the user accepts

Status: accepted (2026-10-05, ticket #387, spec #376). Builds on the agent runtime (ADR 0009), occupation matches (ADR 0010), market briefs (ADR 0011) and pay analysis (ADR 0013).

## Decision

- **Run task `roadmap`**, model-free and allowance-releasing like `market_brief`. Needs a confirmed profile and a goal with a confirmed occupation (409 `CareerOccupationRequired`). Pins profile version, goal version, occupation code, and the latest market brief id and pay analysis id when they exist (null otherwise, recorded as missing evidence).
- **Options only when evidence supports them.** `closest_fit` (the confirmed occupation) is always produced. `higher_ambition` is produced only when the confirmed match lists another candidate whose BLS national median is at least 10 % higher and that has at least one duty-evidence item; `steadier_transition` only when a candidate has projected change ≥ the target's and a median within ±15 %. Missing support yields fewer options with a stated reason, never invented ones.
- **Each option carries** rationale (cited figures and their source release), assumptions, missing evidence, and a scenario timeline labelled "a scenario, not a promise". No salary uplift, no credential the user lacks presented as held, no paid course as a requirement (tasks are worded as free actions; the generator has no course/price vocabulary).
- **Tasks** for "this week" plus 30/60/90-day milestones are generated from a fixed template library keyed by the gaps (missing evidence, known gaps from the match). Effort per task is in hours and fitted to the goal's `weeklyEffortHours`: when total week-one effort exceeds it, tasks spill into later milestones; with < 2 hours/week the plan says so and keeps one task per week. Dependencies are validated as a DAG (cycles rejected with `CareerRoadmapCycle`, unknown ids rejected).
- **Persistence and acceptance.** `CareerRoadmap` (owner-scoped, versioned per goal: `Version` increments per new roadmap) with status `proposed | accepted | dismissed`. Accepting requires the chosen option key and the goal's `If-Match`; it records the selection on the roadmap and **does not change the goal's occupation or location** (no silent goal change); if the chosen option is not the closest fit, the response says the goal is unchanged and links to the occupation page. Editing a task's effort writes a new roadmap version. Reads compute `stale` with reasons (profile/goal/occupation/brief changed).
- **Privacy.** Owner cascade, `CareerPrivateDataService` coverage, retained while the account exists; export with #392.
